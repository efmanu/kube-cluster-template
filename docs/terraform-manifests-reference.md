# Terraform & Manifest Reference

A file-by-file explanation of everything that builds and runs the cluster. Read alongside
`kubernetes-cluster-guide.md` (the narrative) and `kubectl-cheatsheet.md` (the commands).

- **`terraform/`** — creates the 2 BinaryLane servers and auto-installs k3s on them.
- **`manifests/`** — the Kubernetes objects that make up the demo stack, in the `dev` namespace.

---

## Part A — Terraform (`terraform/`)

| File | Purpose |
|------|---------|
| `main.tf` | The root module: declares the provider and the two server resources. |
| `variables.tf` | All input variables (with types/defaults). |
| `outputs.tf` | What `terraform apply` prints at the end. |
| `templates/control-plane.yaml.tftpl` | cloud-init script for the control-plane node. |
| `templates/worker.yaml.tftpl` | cloud-init script for the worker node. |
| `terraform.tfvars` | Your **real** secret values (gitignored). |
| `terraform.tfvars.example` | A template to copy — safe to commit. |
| `.terraform.lock.hcl` | Pins the exact provider version (generated by `terraform init`). |
| `.gitignore` | Keeps state files and secrets out of version control. |

### `main.tf`

Three blocks:

1. **`terraform { … }`** — the *root module* settings:
   - `required_version = ">= 1.5"` — minimum Terraform CLI version.
   - `required_providers` — downloads `oscarhermoso/binarylane` (the community provider for
     BinaryLane's API), pinned to `~> 0.13`.

2. **`provider "binarylane" { … }`** — configures the BinaryLane API client. It has **no explicit
   token** in the file; it reads the `BINARYLANE_API_TOKEN` environment variable automatically. The
   comment in the file shows how to export it from `src/.env`.

3. **Two `binarylane_server` resources** (the actual VPSs):

   - **`control_plane`** — hostname `k8s-master`, 1 public IPv4, root password, `user_data` =
     `control-plane.yaml.tftpl` (which installs k3s as the **server**). Receives `k3s_token`.

   - **`worker`** — hostname `k8s-worker`, same specs, `user_data` = `worker.yaml.tftpl` (which
     installs k3s as the **agent**). Receives `k3s_token` *and* `master_ip`.

   The critical line is in `worker`:
   ```hcl
   master_ip = binarylane_server.control_plane.public_ipv4_addresses[0]
   ```
   Referencing the control plane's attribute creates an **implicit dependency**: Terraform knows the
   control plane must be created (and have an IP) before the worker's user_data can be rendered. This
   is what guarantees the worker joins an already-running control plane.

### `variables.tf`

| Variable | Type | Default | Purpose |
|----------|------|---------|---------|
| `region` | string | `syd` | BinaryLane region slug. |
| `image` | string | `ubuntu-24.04` | OS image slug. |
| `size` | string | `std-min` | Server size: 1 vCPU / 1 GB RAM / 20 GB disk / 1 TB transfer. |
| `root_password` | string (sensitive) | — | Root password applied to both servers. |
| `k3s_token` | string (sensitive) | — | Shared secret both nodes use to form the k3s cluster. |

`size = "std-min"` was chosen deliberately — it matches the $4.90/mo 1-vCPU plan, not `std-1vcpu`
(which is 2 GB RAM / $9.80).

### `outputs.tf`

Exposes `server_public_ips`, a map `{ "k8s-master" = [...], "k8s-worker" = [...] }`, so after
`terraform apply` you can read both nodes' public IPs directly from the terminal instead of digging
through the BinaryLane dashboard.

### `templates/control-plane.yaml.tftpl`

A `#cloud-config` file rendered by `templatefile()` at apply time. The `${k3s_token}` placeholder is
substituted with the variable value. Its `runcmd` runs once on first boot:

```bash
curl -sfL https://get.k3s.io | K3S_TOKEN='<token>' sh -
```

This installs k3s as the **server** (control plane) with a fixed token. No
`--write-kubeconfig-mode 644` is needed here because `deploy.sh` copies the kubeconfig as root.

### `templates/worker.yaml.tftpl`

Also a `#cloud-config`, but with two placeholders (`${k3s_token}` and `${master_ip}`). Its `runcmd`
does two things:

1. **Waits** for the control plane's API (`https://<master_ip>:6443/ping`) to respond, retrying every
   10s up to ~15 min — this handles the fact that the control plane takes a minute or two to boot and
   install k3s.
2. Installs k3s as the **agent** (worker) that joins the existing cluster:
   ```bash
   curl -sfL https://get.k3s.io | K3S_URL='https://<master_ip>:6443' K3S_TOKEN='<token>' sh -
   ```

### `terraform.tfvars` vs `terraform.tfvars.example`

- `.example` holds **placeholder** values and is safe to commit — copy it to `terraform.tfvars` to
  start.
- `terraform.tfvars` holds your **real** `root_password` and `k3s_token`. It's ignored by
  `.gitignore` so secrets never enter version control.

## Part B — Manifests (`manifests/`)

Applied in numeric order; the numbering encodes the dependency chain (`00` namespace → `01`/`02`
config → `10`/`11` database → `12` API → `13`/`14` frontend).

### `00-namespace.yaml` — `Namespace`

```yaml
kind: Namespace
metadata: { name: dev }
```

**Purpose:** a logical partition named `dev` that isolates this stack from system components
(`kube-system`, etc.) and lets you run `dev`/`staging`/`prod` side by side. Everything else declares
`namespace: dev`. Must exist **before** anything is placed in it.

### `01-secret.yaml` — `Secret`

```yaml
kind: Secret
metadata: { name: db-secret, namespace: dev }
type: Opaque
stringData: { POSTGRES_PASSWORD: change-me-please }
```

**Purpose:** store sensitive data (the Postgres password). `type: Opaque` means arbitrary key/value
pairs. `stringData` lets you write the password in plaintext — Kubernetes base64-encodes it into the
stored object, so it isn't shown by `kubectl describe`. Consumed by the Postgres and API Deployments
via `secretKeyRef`.

### `02-configmap.yaml` — `ConfigMap`

```yaml
kind: ConfigMap
metadata: { name: db-config, namespace: dev }
data: { POSTGRES_DB: demo, POSTGRES_USER: demo }
```

**Purpose:** non-secret configuration (database name + username). Decouples config from the image —
change values here without rebuilding. Consumed via `configMapKeyRef` in the Postgres and API
Deployments. (Note `POSTGRES_DB: demo` is the **database name**, independent of the `dev` namespace.)

### `10-postgres-pvc.yaml` — `PersistentVolumeClaim`

```yaml
kind: PersistentVolumeClaim
spec: { accessModes: [ReadWriteOnce], resources: { requests: { storage: 1Gi } } }
```

**Purpose:** request 1 Gi of durable disk. k3s bundles **local-path-provisioner**, which creates a
`PersistentVolume` on the node's disk automatically — no cloud volume setup. This is what keeps
Postgres data alive across Pod restarts and reschedules.

### `11-postgres.yaml` — `Deployment` + `Service` (database tier)

- **Deployment** (`app: postgres`, 1 replica, image `postgres:16`):
  - Injects `POSTGRES_DB`/`POSTGRES_USER` from `db-config` and `POSTGRES_PASSWORD` from `db-secret`.
  - Mounts the PVC at `/var/lib/postgresql/data` (Postgres's data directory).
- **Service** (ClusterIP, `postgres:5432`): gives the DB a stable internal DNS name (`postgres`) so
  the API reaches it by hostname, no IPs.

Single replica is intentional — a stateful DB needs a StatefulSet + read replicas for multi-replica,
which is beyond this intro.

### `12-api.yaml` — `Deployment` + `Service` (API tier)

- **Deployment** (`app: api`, 2 replicas): currently runs the **public test image**
  `hashicorp/http-echo` on `:3000` so the chain works with no build step. A comment in the file shows
  how to swap it back to the real Node.js image (`<your-user>/demo-api:1.0.0`) and restore the
  `POSTGRES_*` env block (see the guide §7.2) — that's what actually queries the database.
- **Service** (ClusterIP, `api:3000`): the stable address the frontend's nginx proxies to.

### `13-nginx-config.yaml` — `ConfigMap` (nginx config)

```yaml
data:
  default.conf: |
    server {
      listen 80;
      location / { proxy_pass http://api:3000; ... }
    }
```

**Purpose:** inject a custom nginx `default.conf` that reverse-proxies `/` to the `api` Service. The
frontend mounts this ConfigMap over `/etc/nginx/conf.d`, replacing the stock welcome page. `api:3000`
works because of Kubernetes' internal DNS — no IP needed.

### `14-frontend.yaml` — `Deployment` + `NodePort Service` (frontend tier)

- **Deployment** (`app: frontend`, 2 replicas, image `nginx:1.27`): mounts `nginx-config` into
  `/etc/nginx/conf.d`.
- **Service** (`type: NodePort`, `nodePort: 30080`): opens port **30080 on every node** and routes to
  the frontend Pods. NodePort is the simplest way to reach the app from outside without a cloud load
  balancer — that's why you can `curl http://<ANY_NODE_IP>:30080/`.
